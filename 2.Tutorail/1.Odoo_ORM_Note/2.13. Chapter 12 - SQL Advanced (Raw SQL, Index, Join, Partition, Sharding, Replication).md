# PART 1 — Raw SQL in Odoo ORM

## 1.1 Concept

সাধারণত `self.env` দিয়ে ORM use করো। কিন্তু complex/performance-critical query-তে
কখনো **সরাসরি SQL** চালানো দরকার। Odoo-তে এটা `self.env.cr` (cursor) দিয়ে হয়।

```text
self.env.cr  =  database cursor (PostgreSQL connection)
```

## 1.2 How to Write

```python
from odoo import models


class EmployeeReport(models.Model):
    _name = "my.employee"          # Table name

    def get_dept_wise_count(self):
        """Department-wise employee count — raw SQL দিয়ে।"""
        self.env.cr.execute("""
            SELECT department_id, COUNT(*) AS total
            FROM my_employee
            GROUP BY department_id
        """)
        return self.env.cr.dictfetchall()
```

### Cursor-এর main methods

| Method | কাজ |
|--------|-----|
| `cr.execute(sql, params)` | SQL চালায় |
| `cr.fetchone()` | ১টা row (tuple) |
| `cr.fetchall()` | সব row (list of tuple) |
| `cr.dictfetchall()` | সব row (list of dict) ← সবচেয়ে useful |
| `cr.rowcount` | কত row affected |

## 1.3 Parameterized Query (SQL Injection থেকে বাঁচো)

**⚠️ Always parameter use করো** — string concatenate কোরো না:

```python
# BAD — SQL injection risk
self.env.cr.execute(f"SELECT * FROM my_employee WHERE name = '{name}'")

# GOOD — parameterized
self.env.cr.execute(
    "SELECT * FROM my_employee WHERE name = %s",
    (name,),                       # params tuple → safe
)
rows = self.env.cr.dictfetchall()
```

```text
%s  =  placeholder → params auto-escape করে (safe)
```

## 1.4 Tips

1. **Raw SQL ORM-এর security bypass করে** (`ir.rule` record rule apply হয় না) — সাবধানে use করো।

2. **Transaction:** Odoo auto-manage করে; explicit `cr.commit()` সাধারণত দরকার নেই (ও dangerous)।

3. **কখন raw SQL?** → complex JOIN, GROUP BY, window function, bulk update, performance tuning।

4. **কখন ORM?** → simple CRUD, record rule/security দরকার, maintainability।

# PART 2 — Index

## 2.1 Concept

**Index** = database-এর "সূচিপত্র" (book-এর মতো)। একটা column-এ index থাকলে
সেই column দিয়ে search করা অনেক **fast** হয়।

```text
Without index → পুরো table scan (row by row)
With index    → B-tree search (O(log n))
```

## 2.2 How to Write (Odoo)

Odoo-তে field-এ `index=True` দিলে auto index তৈরি হয়:

```python
class Employee(models.Model):
    _name = "my.employee"          # Table name

    name = fields.Char(
        index=True,                # indexed column → search fast
    )

    department_id = fields.Many2one(
        "my.department",
        index=True,                # indexed FK → join/search fast
    )                              # FK → my_department.id (PK)
```

### Manual SQL-এ

```sql
CREATE INDEX idx_employee_name ON my_employee(name);

CREATE INDEX idx_employee_dept ON my_employee(department_id);

-- Unique index (১:১ enforce-এর মতো)
CREATE UNIQUE INDEX idx_emp_passport ON my_passport(employee_id);
```

## 2.3 কখন Index দিবে / দিবে না

```text
Index দাও (WHERE / JOIN / ORDER BY-তে use হয়):
  - FK column (join-এ সবসময় লাগে)
  - যেসব field-এ search/filter হয় (name, email, date)

Index দিও না:
  - ছোট table (scan-ই fast)
  - অনেক write হয় এমন column (index maintain করতে costly)
  - rarely-used column
```

> **Golden Rule:** FK column-এ **সবসময় index** দাও। Join performance অনেক ভালো হয়।

# PART 3 — JOIN (INNER / LEFT / RIGHT)

## 3.1 Concept

JOIN = দুইটা table-কে relation (FK) দিয়ে merge করা। এটাই ORM-এর dotted access-এর
আসল SQL।

```text
employee.department_id.name   (ORM)
        ↓
SQL JOIN employee ⋈ department
```

### Sample Tables

```text
employees                        departments
--------------                   ---------------
id (PK)  name      dept_id       id (PK)  name
1        Ashraful  1             1        AI
2        Tanvir    1             2        Software
3        Karim     2             3        Marketing
4        Rahim     NULL          (Marketing-এ কেউ নেই)
```

## 3.2 INNER JOIN — দুই পাশেই match

```sql
SELECT e.name, d.name AS dept
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;
```

```text
Result (শুধু match করা row):
name       dept
Ashraful   AI
Tanvir     AI
Karim      Software

Rahim     ✗ (dept_id NULL → বাদ)
Marketing ✗ (কেউ নেই → বাদ)
```

> **INNER JOIN = intersection।** দুই পাশেই থাকলেই আসে।

## 3.3 LEFT JOIN — left table-এর সব, right match থাকলে

```sql
SELECT e.name, d.name AS dept
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;
```

```text
Result (সব employee, match না থাকলে NULL):
name       dept
Ashraful   AI
Tanvir     AI
Karim      Software
Rahim      NULL        ← employee আছে, dept নেই
```

> **LEFT JOIN = বামের সব + ডানের match।** NULL মানে "match নেই"।

## 3.4 RIGHT JOIN — right table-এর সব

```sql
SELECT e.name, d.name AS dept
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id;
```

```text
Result (সব department):
name       dept
Ashraful   AI
Tanvir     AI
Karim      Software
NULL       Marketing   ← department আছে, employee নেই
```

> **RIGHT JOIN = ডানের সব + বামের match।** (অনেকে LEFT-এই লিখে, RIGHT rare)

## 3.5 FULL OUTER JOIN — দুই পাশেরই সব

```sql
SELECT e.name, d.name AS dept
FROM employees e
FULL OUTER JOIN departments d ON e.dept_id = d.id;
```

```text
দুই পাশের সব row (match না হলে NULL)
```

## 3.6 Visual Summary

```text
INNER JOIN    →  A ∩ B     (দুই পাশের common)
LEFT JOIN     →  A সব + B match   (A ∪ (A∩B))
RIGHT JOIN    →  B সব + A match
FULL OUTER    →  A ∪ B     (সব)
```

| JOIN | Result |
|------|--------|
| INNER | শুধু match |
| LEFT | left সব + right match (NULL) |
| RIGHT | right সব + left match (NULL) |
| FULL OUTER | দুই পাশের সব |

> **ORM-এর relation access = JOIN।** `Many2one` dotted access মূলত LEFT JOIN-এর মতো কাজ করে।

# PART 4 — Partition

## 4.1 Concept

**Partition** = একটা বড় table-কে **logical ছোট টুকরা**-য় ভাগ করা (same database-এ)।

```text
big table (orders — ১০ কোটি row)
      ↓
partition by date
      ↓
orders_2023, orders_2024, orders_2025 ...
```

Query শুধু relevant partition scan করে → **fast**।

## 4.2 Types

```text
RANGE  → date/range দিয়ে (orders by year/month)
LIST   → category দিয়ে (region: US/EU/ASIA)
HASH   → id % N দিয়ে (evenly distribute)
```

## 4.3 How to Write (SQL)

```sql
-- Range partition (by order_date)
CREATE TABLE orders (
    id SERIAL,
    order_date DATE NOT NULL,
    customer_id INT,
    ...
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

```text
orders (parent)
   ├── orders_2023  → 2023-এর data
   ├── orders_2024  → 2024-এর data
   └── ...
```

Query `WHERE order_date = '2024-05-01'` → শুধু `orders_2024` scan করে।

## 4.4 Tips

1. **কখন partition?** → খুব বড় table (মিলিয়ন+ row) + time-based query (log, order, transaction)।

2. **Partition ≠ Sharding** — partition **same DB**-তে table ভাগ, sharding **different DB**-তে data ভাগ।

3. **PostgreSQL**-এ native partition support (Odoo-র database)।

# PART 5 — Sharding

## 5.1 Concept

**Sharding** = data **multiple database server**-এ horizontal ভাগ করা (scale out)।

```text
১টা DB server (সব data)
      ↓
shard key দিয়ে ভাগ
      ↓
Shard 0 (users A-M)   Shard 1 (users N-Z)   Shard 2 (...)
```

## 5.2 Shard Key

কোন column দিয়ে ভাগ হবে সেটা:

```text
shard = hash(customer_id) % 3

customer_id 101 → shard 0
customer_id 102 → shard 1
customer_id 103 → shard 2
```

## 5.3 Partition vs Sharding

```text
Partition   → same DB, same server, table-level split
Sharding    → different DB, different server, data-level split

Partition = vertical (১ server-এ organize)
Sharding  = horizontal (multiple server-এ scale)
```

## 5.4 Tips

1. **Sharding complex** — join across shard কঠিন, transaction distributed হয়।

2. **কখন sharding?** → এক server-এ capacity শেষ (FB, Twitter-level scale)। ছোট/মাঝারি app-এ partition + replica-ই যথেষ্ট।

3. **Odoo নিজে sharding করে না** — এটা infrastructure-level decision।

# PART 6 — Master-Slave (Replication)

## 6.1 Concept

**Master-Slave replication** = একটা primary DB (master) + একাধিক copy (slave)।

```text
          WRITE (INSERT/UPDATE/DELETE)
                     ↓
              ┌── MASTER (primary) ──┐
              │   (write-এর source)  │
              │          │           │
              │   replication (copy) │
              │          ↓           │
              └──► SLAVE (read copy) ┘
                          ↑
            READ (SELECT) — slaves থেকে serve
```

## 6.2 Read/Write Split

```text
Master → সব WRITE (create/update/delete)
Slave  → সব READ (search/browse)

কারণ read সাধারণত অনেক বেশি হয় → slave-এ distribute করে load কমানো।
```

## 6.3 Key Concept

| Term | মানে |
|------|------|
| **Master** | primary DB — write এখানে হয় |
| **Slave/Replica** | copy DB — read serve করে |
| **Replication** | master → slave data copy (async) |
| **Replication lag** | master-এ write → slave-এ পৌঁছাতে delay |

## 6.4 Tips

1. **Read-heavy app-এ** master-slave split performance অনেক বাড়ায়।

2. **⚠️ Replication lag:** master-এ এইমাত্র write করা data slave-এ সাথে সাথে নাও থাকতে পারে। "write-র পরেই read" হলে master থেকে read করতে হয়।

3. **Odoo-তে read replica:** Odoo PostgreSQL replica use করা যায় read-এর জন্য (advanced infra setup)।

4. **Failover:** master down হলে slave-কে promote করে master বানানো যায় (high availability)।

# Quick Recap — পুরো Chapter এক নজরে

```text
Raw SQL      → self.env.cr.execute() + parameterized (%s)
Index        → field(index=True) / CREATE INDEX → search fast
              → FK column-এ always index

JOIN         → INNER (match), LEFT (left সব), RIGHT (right সব), FULL (সব)
              → ORM dotted access = JOIN

Partition    → big table same DB-তে ভাগ (date/category/hash)
Sharding     → data multiple server-এ ভাগ (scale out)
Master-Slave → master write + slave read + replication
```

```text
                  ┌─ Raw SQL ── self.env.cr
                  │
Performance  ─────┼─ Index ──── index=True
                  │
                  ├─ JOIN ───── INNER/LEFT/RIGHT/FULL
                  │
Architecture ─────┼─ Partition ─ same DB split
                  │
                  ├─ Sharding ── multiple DB
                  │
                  └─ Master/Slave ─ read/write split
```

> **Super Rule:** ORM-র নিচে SQL, SQL-এর নিচে PostgreSQL। Performance problem হলে
> **index → query optimize → partition/replica** এই order-এ ভাবো।
