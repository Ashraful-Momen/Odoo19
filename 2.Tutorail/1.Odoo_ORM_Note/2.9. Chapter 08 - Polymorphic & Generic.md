# Chapter 08 — Polymorphic & Generic Relation

> **Golden Rule:** Normal FK একটা নির্দিষ্ট table-কে point করে। Polymorphic relation
> **`(model, id)`** দুটো column দিয়ে **যেকোনো** table-কে point করে।

```text
Normal FK     → employee_id → hr.employee (fixed table)
Polymorphic   → res_model + res_id → যেকোনো model
```

## 1. Problem — Attachment যেকোনো object-এর হতে পারে

একটা **Attachment** (file) যেকোনো object-এর হতে পারে:

```text
Employee
Invoice
Product
Customer
Sale Order
```

Normal FK দিলে প্রতিটার জন্য আলাদা column লাগে:

```text
attachment
-----------------
employee_id
invoice_id
product_id
customer_id
order_id
```

এটা **messy** — যত model আসবে তত column বাড়বে।

### Solution → Polymorphic

```text
attachment
---------------
res_model
res_id
```

২টা column-এই **যেকোনো model + record** ধরা যায়।

---

## 2. res_model + res_id Concept

```text
res_model  = কোন model?    (string, যেমন "hr.employee")
res_id     = কোন record?   (integer, যেমন 10)
```

### Data Example

```text
attachment
----------------------------------
id   name         res_model         res_id
1    CV.pdf       hr.employee       10
2    Invoice.pdf  account.move      50
3    Image.png    product.product   20
```

```text
Row 1 → hr.employee  record #10  →  "CV.pdf"
Row 2 → account.move record #50  →  "Invoice.pdf"
Row 3 → product.product record #20 → "Image.png"
```

> একই attachment mechanism **অনেক model**-এর সাথে কাজ করে।

## 3. Odoo Model-এ Polymorphic লেখা

Odoo-তে `ir.attachment` এই concept-এর classic example। নিজে বানাতে:

```python
from odoo import models, fields


class MyAttachment(models.Model):
    _name = "my.attachment"        # Table name

    # id = PK → Odoo auto-create

    name = fields.Char()           # file name

    res_model = fields.Char()      # polymorphic → কোন model (string)

    res_id = fields.Integer()      # polymorphic → কোন record id

    # ⚠️ res_id কোনো normal FK নয় — runtime-এ res_model দেখে target ঠিক হয়
```

### Full ASCII — Polymorphic relation

```text
  my.attachment
┌─────────────────────────────┐
│ id (PK)                     │
│ name                        │
│ res_model = "hr.employee" ──┼──► hr.employee  (id = res_id)
│ res_id    = 10              │
│                             │
│ res_model = "account.move" ─┼──► account.move (id = res_id)
│ res_id    = 50              │
└─────────────────────────────┘

         এক column-pair → অনেক different model
```

## 4. Generic Relation কী?

Generic relation আর polymorphic relation অনেক context-এ কাছাকাছি।

```text
Traditional FK:
    employee_id  →  hr.employee

Generic:
    model = "hr.employee"
    id    = 10
```

```text
Traditional FK        Generic
----------------      -----------------
employee_id           model + id
   ↓                      ↓
employee              যেকোনো model
```

> **Definition:** একটা relation যেখানে target model **fixed নয়**; runtime-এ `model + id` দিয়ে identify করা হয়।

---

## 5. Polymorphic vs Normal FK

### Normal FK

```text
comment
---------
id
employee_id   → শুধু Employee-এর সাথে relation
```

শুধু একটা model-এর comment হতে পারে।

### Polymorphic

```text
comment
---------
id
res_model
res_id        → Employee, Invoice, Product, Order সবকিছুর
```

সবকিছুর comment হতে পারে।

---

## 6. Important Warning — Referential Integrity

Normal FK-এর মতো database-level referential integrity polymorphic-এ **সহজে enforce করা যায় না**।

```text
res_id = 10
```

কিন্তু:

```text
10 কোন table-এর?
```

সেটা `res_model` বলে। Database সাধারণ FK constraint-এর মতো:

```text
res_id → multiple possible tables
```

enforce করতে পারে **না**।

তাই **application/ORM-level validation** গুরুত্বপূর্ণ।

> Odoo-তে `ir.attachment`-এ `res_model` + `res_id` আছে, কিন্তু database-এ এটা plain `Char` + `Integer` — **কোনো real FK constraint নেই**।

---

## 7. Tips & Tricks

1. **Polymorphic চেনার signal:** `res_model` + `res_id` (বা `model` + `id`) field pair দেখলেই বুঝবে।

2. **Odoo-তে common examples:**
   ```text
   ir.attachment   → res_model + res_id
   mail.message    → model + res_id (activity/message)
   ```

3. **কখন polymorphic ব্যবহার করবে?** → একটা relation যখন **অনেক আলাদা model**-এর সাথে লাগতে পারে (comment, attachment, activity, note)।

4. **কখন ব্যবহার কোরো না?** → target model **fixed** হলে normal FK (`Many2one`) ব্যবহার করো — fast + referential integrity থাকে।

5. **Data integrity নিজে handle করো:** polymorphic field-এ value set করার সময় `res_model` valid কিনা check করো।

---

## 8. Quick Recap

```text
Polymorphic
  ↓
(model + id) → যেকোনো model
  ↓
res_model (Char)  +  res_id (Integer)
  ↓
Example: ir.attachment

Normal FK      → একটা fixed table
Polymorphic    → অনেক possible table (runtime-এ ঠিক হয়)

Warning: database-level FK constraint থাকে না → ORM-level validation
```

> **Super Rule:** Normal FK = fixed target। `res_model` + `res_id` = dynamic target (polymorphic/generic)।
